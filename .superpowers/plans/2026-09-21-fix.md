盤點完 66 個 src 專案後的結論：**這個框架的「廣度」遠超「深度」**——模組清單看起來對標 ABP，但相當一部分是介面與空模組，真正缺的不是新功能域，而是把既有抽象落地。

## 一、名存實亡的三個模組（最該優先補）

**1. Validation 模組是空的**
[XiHanValidationModule.cs](framework/src/XiHan.Framework.Validation/XiHanValidationModule.cs) 整個 `ConfigureServices` 沒有任何註冊（連取到的 `config` 都沒用）。整個「數據校驗庫」只有 `XiHanValidationException` + `IHasValidationErrors` 兩個型別，共 158 行。

缺的是：應用服務層自動驗證管線、FluentValidation/DataAnnotations 適配、驗證訊息本地化（Localization 已就緒卻沒接）、`IObjectValidator` 這類可在非 Web 入口（Job、MQ 消費）復用的驗證入口。目前驗證完全依賴 MVC 的 `ModelState`，等於**只有 HTTP 請求受保護**。

**2. Traffic 的限流與熔斷只有介面**
[XiHanTrafficServiceCollectionExtensions.cs](framework/src/XiHan.Framework.Traffic/Extensions/DependencyInjection/XiHanTrafficServiceCollectionExtensions.cs) 只註冊灰度路由。`IRateLimitPolicy`、`ICircuitBreakerPolicy` 零實作、零註冊、零中介軟體。

而 Web.Api 另起爐灶做了自己的 [CircuitBreaking/](framework/src/XiHan.Framework.Web.Api/CircuitBreaking/) 與 [RateLimiting/](framework/src/XiHan.Framework.Web.Api/RateLimiting/)。兩套並存、互不相干：抽象在基礎設施層，實作在 Web 層，等於**分層被架空**，而且限流狀態是進程內的，多實例部署下閾值會被乘以實例數。缺的是分散式限流（Caching 模組已有 Redis Lua 腳本能力 `ICacheSupportsLuaScript`，現成不用）。

**3. Web.Grpc 只有 66 行**
[XiHanWebGrpcModule.cs](framework/src/XiHan.Framework.Web.Grpc/XiHanWebGrpcModule.cs) 只調了 `services.AddGrpc()`，`OnApplicationInitialization` 取了 `app` 之後什麼都沒做。相比 Web.Api 的動態 API 投影，gRPC 這邊沒有 code-first 服務投影、沒有攔截器接 UoW／審計／租戶解析／異常轉換。等於**引了包但沒有框架能力**。

> 附帶訊號：`Validation.Tests` 442 行、`Web.Grpc.Tests` 540 行——測試矩陣看起來齊全，實際在測空模組。

[framework/src/XiHan.Framework.Data/SqlSugar/](framework/src/XiHan.Framework.Data/SqlSugar/) 這層做得相當紮實（多數據源路由、讀寫分離＋從庫健康檢查、租戶連線推導、差異日誌 AOP、CodeFirst 初始化、種子）。但框架自身所有狀態的 Store **一個都沒有落到資料庫**：

## 三、資料層的具體缺口

- **無批次寫入 API**。全倉庫零 `Fastest<T>()` / `BulkCopy` 使用，[IRepositoryBase](framework/src/XiHan.Framework.Domain/Repositories/IRepositoryBase.cs) 的 `AddRangeAsync` 走逐條 Insert。SqlSugar 最大的性能賣點沒暴露出來，萬條匯入場景必須繞過倉儲。
- **分表只做了一半**。`ISplitTableEntity` 在 [DbInitializer](framework/src/XiHan.Framework.Data/SqlSugar/Initializers/DbInitializer.cs#L384) 能建表，但倉儲的查詢／寫入路徑完全沒有 `.SplitTable()`，查分表資料只能自己拿 `ISqlSugarClient`。
- **無行級資料權限**。`DataScope` / `DataPermission` 在全倉庫零命中。多租戶隔離有了，但「只能看本部門／本人／自訂範圍」這種中後台剛需完全沒有，且沒有可掛載的查詢過濾器擴充點。
- **無可開關的全域資料過濾器**。軟刪除與租戶過濾是寫死在 SqlSugar 全域過濾裡的，沒有 ABP `IDataFilter<T>` 那種 `using (dataFilter.Disable<ISoftDelete>())` 的作用域逃生口——管理後台要查已刪資料時無解。
- **無版本化遷移**。只有 CodeFirst 表結構同步 + Upgrade 模組跑 SQL 腳本檔，沒有遷移歷史比對、沒有 down／回滾、沒有「目標環境與程式碼版本不一致」的啟動檢測。

（樂觀鎖這塊是有的：`RowVersion` + [ConcurrencyConflictException 轉譯](framework/src/XiHan.Framework.Data/SqlSugar/Repository/SqlSugarRepositoryBase.cs#L520)，這點沒問題。）

## 四、Web / API 層

- **無冪等性支援**。`Idempotency-Key` 零實作（grep 只命中 Bot 的訊息去重）。對外 API 的重複提交、支付回調重投，框架層完全沒有防線，而 Caching 的分散式鎖是現成的。
- **無 API 版本化**。`ApiVersion` 只出現在動態 API 的路由字串拼接，不是 `Asp.Versioning`。無法多版本並存、無棄用標頭、無版本化的 OpenAPI 文件分組。這對一個「所有前端按約定對接」的動態 API 框架是硬傷。
- **SignalR 沒有 backplane**。[Web.RealTime](framework/src/XiHan.Framework.Web.RealTime/) 的 csproj 一個 PackageReference 都沒有，`ConnectionManager` 是進程內字典。**多實例部署下推送必漏**，這是會在生產環境炸掉的那類問題。
- **Gateway 名不副實**。[Web.Gateway](framework/src/XiHan.Framework.Web.Gateway/) 只有灰度／追蹤／異常三個中介軟體，沒有 YARP、沒有路由配置、沒有負載均衡、沒有服務發現、沒有請求聚合。實際上是「灰度中介軟體集」，不是閘道。
- **健康檢查沒有端點**。[Observability](framework/src/XiHan.Framework.Observability/Extensions/DependencyInjection/XiHanObservabilityServiceCollectionExtensions.cs#L35) 調了 `AddHealthChecks()`，但全倉庫沒有任何 `MapHealthChecks`；探針只有 `MemoryHealthCheck` 和 SqlSugar 從庫檢查，缺 Redis／MQ／ES 探針，也沒有 liveness/readiness 分離。多處配置把 `/health` 寫進豁免清單，但那個端點根本不存在。

（OTel 這塊反而做得對：tracing/metrics 都接了 OTLP，自研 `MetricsCollector` 的 Meter 也併入了匯出，不是問題。）

## 五、架構層面的一個判斷

橫切關注點（UoW、快取、日誌、響應包裝）**幾乎全掛在 MVC 過濾器上**。Castle 那邊只有 `UnitOfWorkInterceptor` 和 `CacheInterceptor`。結果是：同一個應用服務，從 HTTP 進來享有完整管線，從 Job、MQ 消費者、gRPC 進來則什麼都沒有。

Application 層只有 5 個檔案（CRUD 基類 + `DynamicApiAttribute`），沒有 CQRS／Mediator 管線。補一層與傳輸無關的執行管線（驗證 → 授權 → 事務 → 快取 → 審計），是讓上面那些缺口一次性收斂的結構性解法——而且這正好是 MCP／AI Skill 那條「投影與傳輸解耦」思路的同一套邏輯，框架裡已有先例。

另外兩個較小的缺口：沒有通用的 Feature／功能開關模組（只有租戶級 `ITenantFeatureChecker`）；DevTools 只有命令列解析器，沒有 SqlSugar 系框架通常標配的 CRUD 程式碼產生器。

## 建議優先序

1. **EventBus outbox/inbox 的 SqlSugar 持久化** — 目前是「看起來有可靠投遞，實際沒有」，風險最高
2. **SignalR Redis backplane** — 一行包引用級別的成本，不補就是生產事故
3. **Validation 管線填實** — 空模組，且下游無替代方案
4. **限流／熔斷收斂到 Traffic 並改分散式** — 消除兩套並存
5. **審計 Writer 的 SqlSugar 實作** — 管線都建好了，只差落庫
6. 冪等性、API 版本化、行級資料權限、批次寫入 API

這六項裡 1、2、5 都是「基礎建設已備、只差最後一哩」，投入產出比最高。
